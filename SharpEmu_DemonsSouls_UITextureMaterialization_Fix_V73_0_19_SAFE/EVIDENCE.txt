SOURCE INCONSISTENCIES
======================
1. Windows default GuestImageWriteTracker is disabled unless
   SHARPEMU_GUEST_IMAGE_CPU_SYNC=1.

2. Vulkan IsTextureContentCached() only checked whether a descriptor identity
   existed in a ConcurrentDictionary. It did NOT check whether the guest CPU
   changed the backing texels after the texture was cached.

3. Therefore tiled assets / UI sheets / font atlases whose guest memory changed
   could continue shipping an empty texel payload forever while Vulkan reused
   an old image.

4. IsGuestImageUploadKnown() had an 8x64-byte sparse probe, but ordinary
   _textureCache identities bypassed that logic entirely.

5. Render-thread self-heal TryReadGuestTexturePixels() used only ICpuMemory.TryRead,
   while AGC sampled texture reads already support:
   - normal guest memory
   - tracked libc heap
   - low-46-bit GPU alias of tracked libc heap.

6. ProvideRenderTargetInitialData() also used CpuMemory-only access even though
   its own purpose includes CPU-prefilled UI/overlay layers.

V73.0.19
========
- Sparse 512-byte content generation probe for cached Demon Souls textures when
  write tracking is off.
- Probe is seeded from the exact submitted bytes when possible.
- Changed guest bytes mark the cache identity stale.
- Render thread retires the old VkImage safely after prior batch references and
  creates a new resource from the fresh texels.
- Vulkan self-heal now resolves tracked libc heap and GPU aliases.
- CPU-prefilled render-target initial data uses the same alias-aware reader.
- Does NOT set SHARPEMU_NO_TEXTURE_SKIP, preserving the performance cache.
