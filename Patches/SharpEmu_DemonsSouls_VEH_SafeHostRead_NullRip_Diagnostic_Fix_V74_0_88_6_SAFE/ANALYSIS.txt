SharpEmu Demon's Souls V74.0.88.6 SAFE

V74.0.88.5 changed the failure signature completely.

Observed runtime facts:
- Exit code remains 0xC0000005.
- host_movie_upload_count=0.
- No Bink NIHAV bridge was attached.
- main_menu was never reached.
- The first critical guest failure is an execute access violation at RIP=0 on Core.Res.Decompressor.
- While handling that guest exception, the managed VEH path itself throws:
    System.AccessViolationException
    Marshal.ReadInt64
    DirectExecutionBackend.TryReadHostQword
    DirectExecutionBackend.VectoredHandler

Therefore the V88.5 run does NOT support blaming Vulkan/Bink for this crash.
The host crashes inside its exception diagnostic/recovery path before the movie stage.

V74.0.88.6 repairs the host-side fault without faking guest progress:
- scans every DirectExecutionBackend*.cs partial file;
- locates exactly one TryReadHostQword and one VectoredHandler;
- replaces only TryReadHostQword's body;
- validates address range, VirtualQuery result, MEM_COMMIT, PAGE_NOACCESS,
  PAGE_GUARD, and full 8-byte region bounds before Marshal.ReadInt64;
- leaves VectoredHandler's guest-exception policy unchanged;
- emits VEH_SAFE_READ_REJECT for rejected diagnostic reads;
- if current source structure differs, it fails safely and exports relevant
  source lines to Patches instead of guessing.

The immediate objective is to stop the diagnostic handler from producing a
second, fatal managed AccessViolationException. Once that is removed, the same
runtime can expose what the existing VEH does with the original Core.Res.Decompressor
RIP=0 event and whether that guest null-call remains the next root cause.
