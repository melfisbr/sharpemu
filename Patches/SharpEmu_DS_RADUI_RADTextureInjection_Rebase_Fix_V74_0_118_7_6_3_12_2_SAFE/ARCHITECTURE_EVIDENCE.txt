V3.12 ARCHITECTURE EVIDENCE

1. V3.11 runtime: main_menu used RAD_INTERACTIVE_REGION left_guest_pct=34,
   bottom_guest_pct=13, rad_rect=653,0,1920,940. This exactly matches the visual
   black-left/RAD-right split and proves the region method is composition by clipping,
   not pixel integration.

2. V3.11 runtime: descriptorless_direct_fallback_start occurred for both
   logo_intro_loop.bk2 and main_menu.bk2 because external RAD does not set
   HostMovieBridge.IsTitleLoopCompositeActiveV74081. This explains fullscreen/giant
   title frames and loss of guest overlay ownership.

3. Active source HostMovieBridge explicitly says the UI Binks are not fullscreen owner
   movies and that the guest continuously renders text/menus/animation over them while
   sampling their Y/UV surfaces.

4. Demon's Souls EBOOT/context strings contain CCPLdrBinkSimpleMovie,
   frame_bufs[%d].Plane_%s and 'BinkGPU Agc registerResource error', which supports
   Bink-as-GPU-resource integration. Runtime schedules Bink IO/Bink Snd guest threads.

5. The game's needed module list includes libSceAgc, libSceAgcDriver and libSceVideoOut,
   but no libSceBink system module. Bink belongs to the game/middleware render path;
   VideoOut owns the final display buffer.

6. OFW audits: 643 SELF/ELF modules were structurally verified; all contain encrypted
   SELF data entries and PT_DYNAMIC is inside encrypted payload. Raw decoded ELF count
   was zero. Exact private SDK/OFW function reconstruction is therefore unsupported by
   the available files and intentionally not guessed here.

7. Existing native-rad adapter architecture (when a licensed Bink SDK is supplied)
   already eliminates radvideo64.exe and can feed BGRA in-process. V3.12 keeps that
   future path intact and fixes the external-RAD fallback by moving RAD pixels BEFORE
   guest composition instead of AFTER VideoOut.


8. V3.12.2 REBASE: latest console proves a known partial/prototype state: HostApi
   39EF8601..., Presenter 086EB8CA..., while RadExternal remains 3CDD89DC....
   Those exact files exist in the V3.12 prototype lineage, so this package does
   not guess or fuzzy-patch. It accepts only those exact hashes (or the final
   installed hashes), backs them up, and replaces the trio atomically with the
   final texture-injection implementation.
