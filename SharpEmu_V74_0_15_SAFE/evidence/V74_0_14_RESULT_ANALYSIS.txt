V74.0.14 RESULT ANALYSIS
==========================
Source result: SharpEmu_V74_0_14_FASTBOOT_STABILITY_RESULT_20260815_174450.zip

Confirmed improvements:
- main loop reached in 31.6748 seconds
- observed tbb_limit=2
- standalone texture cache 768 MB did not trim
- ErrorDeviceLost hits=0
- HEAP_CORRUPTION hits=0

Remaining failure:
- natural Bink requests=0; black guest output occurs before startup movie handoff
- 320 MB texture array appeared at 0x000000102A400000
- immediately around this event V74.0.8.1 memory telemetry reported alloc2s_mb=5292
- runtime internal working/private at that sample: 10282/15433 MB
- process-tree peak working/private: 17160.8/22588.5 MB
- runtime internal peak working/private: 17222/22676 MB

Root-cause inference:
TryCreateGuestDrawTexture handles 2D/1D arrays before V74.0.5's non-array snapshot reuse.
A 1024x1024 array with ~320 MB of layer data can therefore be independently copied by
multiple concurrent resource/guest threads before the backend texture-cache publication
becomes visible. 5292 MB / 320 MB is consistent with a burst of many duplicate copies.

V74.0.15 response:
- serialize only >=64 MB array snapshot construction
- reuse the exact immutable byte[] for 500 ms for concurrent equivalent requests
- key includes descriptor identity, array layer count, write generation, and tiled/linear path
- support both GPU-tiled and CPU-linear array upload branches
- retain every layer; no placeholder texture and no content skipping
- bound older V74.0.5 non-array transient cache to 8..32 MB
- test at render_scale=0.25 to reduce non-storage render-target pixel pressure
- retain 768 MB Vulkan texture budget because it removed the V74.0.13.2 device-loss regression
